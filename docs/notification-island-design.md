# Windows 灵动岛的通知与窗口入口

收起时回答「哪个应用有提醒」，展开后回答「我要打开哪个窗口」。例如，微信有两个窗口、通知中心有一条微信提醒时，胶囊只在微信图标上显示一个红点。展开后列出两个窗口，用户选择目标。两行都保留自己的窗口标签，应用级提醒不分摊给任何一个窗口。

## 与现有灵动岛的衔接

| 现有能力 | 通知功能的接入方式 |
| --- | --- |
| Rust 管理线程已有可见性状态机、快捷键、拖动与托盘 | 通知快照独立更新。来消息不会展开、唤醒、取消固定或抢占前台。设置窗口关闭后，原生监听随岛体服务运行 |
| 一个非激活 HWND，Direct2D / DirectWrite 绘制，DirectComposition 执行可反向的展开动画 | 消息绘制在同一个窗口。保留用户的显示器、停靠方向、DIP 尺寸和展开时长。绘制、鼠标命中与 MSAA 操作使用同一份面板布局 |
| 默认收起 156 × 44 DIP，展开 328 × 168 DIP，支持合法的更小尺寸 | 默认展开态左侧保留来源、摘要及固定/隐藏，右侧列出所选应用的窗口。列表超出高度时翻页；窄屏按可用空间排布，空间不足可进入设置中的完整窗口列表 |
| 设置页采用 React 草稿、显式保存和本地预览 | 「通知与消息」复用同一页，浏览器也可模拟提醒。真实权限和可切换窗口仅由 Windows 运行时提供 |

底层定位、跨进程点击穿透、动画反向与设备恢复的背景见[原生渲染设计](island-native-renderer-design.md)。

## 提醒能说明什么

| 实际观察 | 岛上呈现 | 状态如何结束 |
| --- | --- | --- |
| 发现微信或 QQ 的合适顶层窗口 | 提供「微信窗口 1」等入口 | 窗口从枚举结果消失后撤下，点击前再次核对归属 |
| Windows 通知中心有可归属到该应用的提醒 | 应用图标带红点，展开显示「有系统提醒」 | 重新读取通知中心后更新；激活窗口不会替用户清除系统通知 |
| 来源没有可确认的应用标识，或通知权限不可用 | 保留能发现的窗口入口，设置页说明权限状态 | 用户授权或来源恢复时重新获取快照 |
| 目标窗口已退出，或 Windows 拒绝前置 | 返回可读原因，可从设置重新选窗口或从任务栏打开 | 下一次刷新重新核对 |

每个窗口使用进程内唯一的操作 ID 和本次观察期的显示序号。窗口发现基于微信、Weixin 和 QQ 客户端的可见、无所有者顶层窗口。相同进程可能有多个窗口，托盘驻留也可能没有可切换窗口。系统通知按操作系统提供的应用标识归属，使用通知的创建时间和 ID 选择每个来源最新的提醒。现有公开字段不能提供可靠的账号身份或聊天未读总数，因此界面使用窗口标签与应用级红点。[Windows UserNotification 字段](https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.usernotification)

## 交互与隐私

来源识别同时使用当前窗口与 Windows 开始菜单注册的应用标识（AUMID）。从开始菜单获得标识后，即使客户端只驻留托盘，也可归属系统通知。客户端可执行文件须通过本地 Authenticode 校验，发布者为受支持的腾讯签名且产品名与来源相符；目标无效或标识有冲突时跳过该提醒。仅出现在客户端内的弹窗不会产生系统通知红点。

- 直接点击收起态的单窗口来源会尝试切换到该窗口。多窗口来源进入选择。鼠标悬停、岛体空白处点击、固定、拖动及离开后的收起沿用既有设置。窗口激活会重新检查 HWND、PID 和进程创建时间；系统仍可拒绝将其他应用前置。[Windows 前台窗口限制](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)
- 收到新提醒时只短暂强调来源图标。系统关闭动画、应用减少动态效果或使用性能档时保留静态红点。展开的文字、应用名称及设置页的可聚焦窗口按钮提供颜色之外的识别方式。
- 默认只处理来源、ID、时间等元数据。主动开启正文预览后，只为可归属、在有效期内的新提醒提取短摘要。在截短前检测验证码上下文和数字；命中时整条替换为「敏感内容已隐藏」。这也可能遮掉带日期或订单号的普通通知。摘要默认从通知创建时间起保留 8 秒，可调为 1–60 秒。
- 预览到期、关闭来源、隐藏岛体或会话锁定会清理敏感内容。设置页、持久化配置及诊断不接收摘要、窗口标题或原生句柄。模拟按钮使用本地样例，可在授权前检查红点与展开布局。

## 运行链路

1. **来源。** Rust 后台线程接收系统通知变化，以容量为一的唤醒队列合并突发事件，并低频重新枚举窗口。每次读通知前检查授权，获取当前通知快照。监听异常仅影响该来源。
2. **管理。** `manager/messages.rs` 接收最新快照，按窗口重建代次和配置代次丢弃迟到更新。原生窗口接收显示数据，设置页仅接收权限、来源名、窗口 ID 和本地标签的变化。管理命令只对 `main` 开放，激活操作只接受已经登记的 ID。
3. **绘制。** 原生消息层用同一份逻辑坐标绘图和建立点击区域。设置预览独立运行；桌面提醒无需经过 WebView 的定时器或逐帧 IPC。
4. **配置。** `IslandConfig.notifications` 随 v2 配置保存。v0、v1 文件补齐默认通知组，沿用原有 revision、锁和备份。权限以及 HWND、PID、应用消息内容均属于运行时数据。

## 安装与系统权限

| 运行方式 | 窗口入口 | 系统通知 |
| --- | --- | --- |
| 浏览器打开设置页 | 本地示例 | 本地示例 |
| 普通开发进程、MSI 或 NSIS 安装 | Windows 原生发现和切换 | 缺少包身份时显示当前安装方式不支持 |
| 带仓库清单的 x64 MSIX | Windows 原生发现和切换 | 已获授权即可读取；系统报告尚未授权时可在设置页主动请求 |

可选 MSIX 清单声明 `userNotificationListener`。Windows 授权针对用户的系统通知，应用在本地仅处理启用的来源。首次授权从设置窗口的 UI 线程发起；拒绝后可打开 Windows 通知隐私设置。已有 MSI/NSIS 用户可继续沿用原安装方式。[微软通知监听说明](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)

**生成可签名的包。** 在已安装 Windows SDK 且能找到 `MakeAppx.exe` 的 x64 开发者 PowerShell 中，从仓库根目录运行以下命令。发布者参数填写实际签名证书的 Subject。若 Cargo 使用自定义输出目录，向脚本传入 `-Executable` 指定 x64 Release 可执行文件。

```powershell
pnpm tauri build --no-bundle
./scripts/package-notification-msix.ps1 -Publisher "CN=实际发布者"
```

默认输出 `src-tauri/target/zx-once.msix`。交付前使用与发布者匹配的受信任证书签名，再安装并从开始菜单的包入口启动。目标机器需要 WebView2。MSIX 的数据目录和启动项受包身份约束，跨安装方式切换时应保留现有配置备份。[Windows 桌面应用打包](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-manual-conversion)

## 桌面交互验收记录

2026-11-12 在 Windows 交互桌面启动独立配置的 Tauri 开发实例，保留默认悬停展开。使用两个模拟微信窗口、一个模拟 QQ 窗口，经过实际 Win32 窗口发现、岛体鼠标点击和系统前台切换。前台观测只记录这三个测试窗口。

| 操作 | 实际结果 |
| --- | --- |
| 从收起态点击微信，随后在岛外点击 | 156 × 44 DIP 胶囊展开为 328 × 168 DIP 面板，两条窗口入口可见；点岛外后恢复胶囊 |
| 在微信列表依次点第一行、第二行、第一行 | 系统前台依次为测试窗口 1、2、1，岛上选中标签也随之更新 |
| 从收起态直接点击只有一个窗口的 QQ | 首轮仅选中来源。修复后一次点击即前置唯一的 QQ 窗口；展开态仍可单独切换来源 |

修复将唯一窗口的操作 ID 绑定在收起态图标上。即使鼠标进入先触发展开，随后处理点击时仍能找到当时命中的目标。此情形已加入 Rust 回归测试。前端 12 项通过，Rust 默认套件 31 项通过，另有 2 项热键和 D3D11 专项在交互桌面单独通过。

## 签名 MSIX 与真实消息的验收记录

2026-11-12，在 Windows 11 26H2（26300.9974）为当前用户安装签名 MSIX，从包入口启动。Windows 签名校验通过，设置页显示「已获准读取系统通知」，正文预览保持关闭。此次安装直接取得已允许状态，未出现需要确认的首次授权弹窗。

| 真实消息 | 收起态胶囊的结果 |
| --- | --- |
| 微信 4.2.0.52 收到一条仅在微信内弹出的消息 | 用户确认 Windows 通知中心没有此条记录。微信、QQ 红点都保持关闭。微信系统提醒的亮起与清除尚未实测 |
| QQ 9.9.37 收到一条保留在 Windows 通知中心的提醒 | 旧包漏标；更新到同一包身份的修复版后，保留的同一条提醒点亮 QQ 红点，微信红点保持关闭 |
| 用户从 Windows 通知中心移除最后一条 QQ 提醒 | 收起态 QQ 红点从亮变灭，微信红点始终关闭 |

红点通过原生胶囊自身的辅助功能状态核对。验收结束后已卸载测试包，并核对机器级临时信任、个人签名证书和关联私钥均已移除。

## 后续实机验收

| 场景 | 应观察到的结果 |
| --- | --- |
| 两个微信窗口、一条微信通知，同时收到 QQ 提醒 | 两个应用各有红点；微信窗口分别可选；移除某应用最后一条通知仅清该应用标记 |
| MSI、签名 MSIX 的首次授权、拒绝、撤销及恢复 | 设置页能区分安装方式受限与用户拒绝，现有窗口入口继续可用 |
| 预览关闭、分隔数字验证码、超时、锁屏和恢复 | 关闭时不解包正文；开启时遮码先于绘制；恢复时不回放已清理的摘要 |
| 快速移入移出、拖动、侧边停靠、混合 DPI、多屏热插拔 | 指针命中跟随可见区域，透明区可穿透，窗口切换不会落到旧实例 |
| 空闲与通知突发 | 空闲不持续呈现新帧；记录通知到可见红点的延迟、P95 帧耗时、CPU 与内存变化 |

窗口发现与激活、签名包获得通知访问、真实 QQ 提醒的归属与清除已有上述记录。微信系统提醒、授权拒绝与撤销，以及混合 DPI 和性能指标仍待对应环境验证。历史渲染数据见[性能基线](island-performance-baseline.md)与[迁移报告](island-performance-report.md)。
